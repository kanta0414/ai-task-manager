# テスト

## 実行方法

```bash
# Backend（要 createdb ai_task_manager_test）
cd backend && ./.venv/bin/python -m pytest -q

# Frontend
cd frontend && npm test

# LLM の Tool 選択評価（実際の LLM を呼ぶ。既定では実行されない）
cd backend && ./.venv/bin/python -m pytest -m llm -v
```

## 方針

**外部に依存するものは偽物に差し替え、依存しない部分を厚くする。**

| 対象 | 方法 |
| --- | --- |
| LLM | `FakeProvider` に差し替え。応答を台本で与え、渡された内容を検証する |
| Google カレンダー | `FakeCalendarClient` に差し替え |
| Celery | タスクは薄いラッパーにとどめ、処理本体（Service）を直接テストする |
| DB | 開発用とは別の `ai_task_manager_test` に対して実行し、テストごとにロールバックする |

この結果、**通常のテストはネットワークもブローカーも不要**で、数秒で終わる。

### アーキテクチャをテストで縛る

要件定義書 32.2「LLM から直接SQLを実行させない」を、コード構造そのもので担保している。

```python
def test_llm_tools_cannot_reach_the_database_directly():
    source = inspect.getsource(tool_registry)
    for forbidden in ("select(", "text(", "self.db.execute"):
        assert forbidden not in source
```

## LLM の Tool 選択評価

開発手順 Phase 18 の「LLM が正しい Tool を選択できるか」に対応する。

**これは単体テストではなく評価。** 実際の LLM を呼ぶため結果は揺れるし遅い。
既定の `pytest` からは除外してあり、`-m llm` を付けたときだけ実行される。

```
入力                                    期待する Tool
「SPIの勉強というタスクを追加して」      create_task
「今日のタスクを教えて」                  search_tasks
「未完了のタスクを教えて」                search_tasks
「明日の予定を教えて」                    search_events
「明日の14時から2時間、〜の予定を入れて」 create_event
「明日2時間空いている時間を探して」       find_free_time
「〜を必要な作業に分解して」              create_subtasks
```

`qwen3:1.7b`（ローカル / CPU）での結果は **7件すべて成功**（実行時間 約7分）。
単発の指示であれば小型モデルでも Tool 選択は安定する。

### 既知の限界（xfail として記録）

多段の指示は現状のモデルでは安定しないため、`xfail` で記録している。
実装の不具合ではなくモデルの能力の問題で、より大きなモデルに変えて成功すれば
`XPASS` として気づける。

| 入力 | 期待 | 実際に起きること |
| --- | --- | --- |
| 「空いている時間にタスクを配置して」 | `generate_schedule` | 「調べる」と「配置する」の区別がつかず `find_free_time` を選ぶ |
| 「ESのタスクを削除して」 | `search_tasks` | 対象を検索せず ID を推測して `delete_task` を呼ぶ |

失敗時は実際に選ばれた Tool 名を出力するため、切り分けができる。
